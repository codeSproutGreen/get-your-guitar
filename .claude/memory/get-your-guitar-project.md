- **The app is named "got-you-bass"** since 2026-09-21 (launcher label and APK file name; icon from the user-supplied `icon.png` at the repo root, regenerated with `scripts/make-launcher-icon.py`). The repo name `get-your-guitar` and the package `com.sproutgreen.getyourguitar` deliberately stay — changing the package would make it a different app on the phone.
- The app is a **bass guitar fretboard simulator** for the user's own practice (not for store release), modeled on the app **"Bass Guitar Solo"**. Reference screenshot: `reference.webp` in repo root.
- **v1 design spec (user-approved 2026-09-16):** `docs/superpowers/specs/2026-09-16-get-your-guitar-v1-design.md`. Read it before any implementation work; it has milestones M0–M3 in section 9.
- **v1.0.0 released 2026-09-21** as a GitHub Release (tag `v1.0.0`, APK asset) at the user's request, containing M0 + M1 + bending only — M2 (settings/tone sliders) and M3 (metronome) are NOT in it even though the spec calls the whole M0–M3 set "v1". Release builds use R8 and are signed with the building PC's Android debug key (no real keystore by design — it could not live in the repo); so build releases on SDS PC only, bump `versionCode` each time, and smoke-test the minified APK on the phone before publishing.
- **M1 "first sound" implemented 2026-09-21 on SDS PC**: core/music, core/synth (Karplus-Strong with loop-filter phase-delay compensation, tuning within 1 cent), core/engine (lock-free SPSC queue), app/audio (AudioTrack low-latency; S10e grants a FAST float track, 16 ms reported latency), app/ui/fretboard. 56 core + 22 app unit tests. What only a human can check (sound, felt latency, multi-touch, upper-register sustain) is open in `docs/verification-checklist.md`. User listened on the S10e 2026-09-21: sound good, latency "almost none", chords work, upper frets "a little short" → fixed by scaling the loop cutoff with sqrt(noteHz/E1) (G4 −56 → −20 dB/s, E1 unchanged); re-listen pending. If still short, raise the decay default (0.7 → ~0.85) rather than touching the filter again. M2 plan: `docs/superpowers/plans/2026-09-21-m2-tone-and-settings.md`.
- **M0 scaffold implemented 2026-09-18 on SDS PC** (Gradle 9.7.0, AGP 9.4.0, Kotlin 2.4.20, Compose BOM 2026.09.00, JUnit 6.1.3). **compileSdk is 37, not the spec's 36** — androidx.core 1.19 / Compose 1.12 require API 37; targetSdk 36 unchanged. **minSdk lowered 33→31 on 2026-09-21** because the SDS PC test phone is a Galaxy S10e on Android 12 (API 31); nothing in the v1 design needs API 32/33. On-device launch verified 2026-09-21 on the Galaxy S10e test phone (see [[sds-verification-env]]); 아키랩 JDK 17 build still unconfirmed.
- Key decisions: Kotlin + Jetpack Compose (Canvas fretboard); `:core` pure Kotlin/JVM module (music theory, Karplus-Strong synth, metronome, engine — unit-tested in 아키랩) + `:app` Android module; audio via `AudioTrack` low-latency (approach "C": output behind `AudioOutput` interface so Oboe can replace it later); minSdk 31 (was 33), compileSdk 37 (was 36); 4-string EADG fixed; tap = pluck with natural decay, fretboard drag = slide/rake, strip drag = scroll with snap; 12 equal-width frets per view.
- **Bending was pulled forward from v2 and implemented 2026-09-21** at the user's request ("현을 위로 당기거나 내리는 기능"). Rule after same-day device feedback ("더 당기면 벤딩이 풀린다"): bend vs rake is decided by *how the gesture starts*, not how far it goes — touch-then-push = bend, touch-and-sweep = rake. Once a non-zero Bend has been sent the pointer is locked to that string until lift (no rake, bend holds at max, visual follows the finger up to 1.5 bands). Crossing bands *before* a bend starts is still a rake. Accepted cost: a slow rake (>80 ms in the first band) reads as a bend. Details that matter: bend arms 80 ms after touch and re-anchors there (protects the first string of a fast rake), strings entered by rake never bend, dead zone 0.1 band, max 200 cents at 0.5 band, release on lift. M2 must NOT apply the slide energy dip to bends.
- **Implemented 2026-09-21 after those requests (not yet released; next release would be v1.1.0, versionCode 2):** (a) tone: plucked-string pulse excitation + pickup comb + amp filter + linear-knee limiter, tuned by measuring band levels — lesson: a physically correct waveform puts its energy in the fundamental, which phone speakers (<250 Hz) cannot play, so mid-band level must be checked or the phone sounds worse; fixed with +6 dB output. (b) hold-to-sustain — first built as a settings switch, then the same day the user asked to expose it as a **long mute bar under the fretboard instead**: while the bar is held a note sounds only while its finger is down; not held = natural decay (the default again, decay default back to 0.7); pressing the bar cuts every string no finger is holding ("뚝", 30 ms) but not notes still held. The settings switch and its stored key were removed. Pull-off now works regardless of mute. Mechanism: per-string finger stacks with ownership give hammer-on/pull-off for free; NoteOff is a 45 ms output fade. (c) settings screen with volume/brightness/decay sliders, bend range, buffer size, test tones; DataStore persistence; `AppState` instead of a ViewModel. User explicitly deferred metronome and the rest of the backlog. Details: `docs/superpowers/specs/2026-09-21-v2-features.md` section 6. Human listening checks are open in the checklist ("v1.1 후보").
- **The end client is a bass player** (the user relays their feedback). 2026-09-21 they reported that rake and bend were not being told apart, and defined them: rake = move vertically *as soon as* you touch; bend = touch, *then* move vertically. Root cause: the old rule armed bending 80 ms after touch regardless of whether the finger had been moving, so any rake slower than ~100 ms per string (i.e. every human rake) became a bend — and I had only ever tested 50 ms-per-string swipes. New rule (user asked for a longer window than my proposed 150 ms): within `SETTLE_MS` = 250 ms of touch, moving >= `RAKE_TRAVEL_BANDS` = 0.25 band (~2.5 mm, above finger-landing jitter) makes it a rake finger for good; otherwise it is a settled finger whose vertical movement is always a bend, locked to its string. While verifying, found and fixed phantom fingers: a system-cancelled gesture never produced `changedToUp()`, leaving a holder in the ownership stacks (fake pull-offs, notes that would not mute). Verify gestures at human speeds and check the phone is idle before injecting touches.
- **Requests received 2026-09-21 after v1.0.0, from someone the user is showing the app to** (the user relays them): (1) a note must sound only while the finger is held, stop on lift — this reverses the v1 "natural decay" decision; (2) "the sound is bad / where did it come from". Answer given: no samples or libraries, real-time Karplus-Strong in `:core`; likely causes are phone-speaker bass roll-off (open strings 41–98 Hz), white-noise excitation, no pickup/body EQ, and the always-nonlinear soft clip. Draft scope and options are in `docs/superpowers/specs/2026-09-21-v2-features.md` (awaiting user decisions; nothing implemented). Proposed order: tone improvements with offline WAV A/B renders → hold-to-sustain → settings → metronome.
- **v2 backlog with hooks already in the v1 design:** real fret spacing with toggle (`FretLayout` interface, v1 = `EqualFretLayout`), sample-based voice, 5-string/tunings, recording.
- Implementation plan documents go in `docs/superpowers/plans/`.

**Why:** The user explicitly asked that v2 features (bending, real spacing) be designed for now but built later; the spec records the hooks so they aren't lost.

**How to apply:** Follow the spec's milestone order (M0 scaffold → M1 first sound → M2 settings → M3 metronome). Every milestone ends with push + verification in the device environment; 아키랩 only verifies `:core:test` and `:app:assembleDebug`. Related: [[archilab-dev-workflow]]
